Are there possible advantages which the first way of the pipeline could provide me with?

MAIN

Yes. Your current pipeline (word → phoneme → rhyme) actually has several important advantages. Even if you later introduce the phoneme-stream architecture, the current approach is still valuable and should probably remain as a separate subsystem.

Below are the real advantages.

1. Much Lower Computational Complexity

Current pipeline compares words, not phoneme windows.

Approximate complexity:

Word-based

O(N²)

where N = number of end-line words.

Example:

16 lines → 16 words → 120 comparisons

Phoneme window approach

O(P² × W)

where

P = number of phonemes
W = window sizes

Example:

120 phonemes × sliding windows
→ thousands of comparisons

So your current pipeline is very fast and scalable.

2. Reliable End-Rhyme Detection

Your current architecture is perfectly optimized for this task:

end rhyme schemes

Example:

A A B B

which is common in:

poetry
songwriting
rap hooks

The phoneme-stream system would detect many internal matches that may not correspond to the intended rhyme scheme.

3. Easier Evaluation

Your Milestone 4 benchmark works because rhymes are word-level objects.

Example evaluation row:

WORD
PHONEMES
RHYME_UNIT
EXPECTED_CLUSTER
PREDICTED_CLUSTER

With phoneme spans, evaluation becomes much harder:

span start
span end
overlap scoring

So the current pipeline is much easier to debug and benchmark.

4. Clean Linguistic Interpretation

Your system currently relies on a classic phonological concept:

rhyme = stressed vowel + coda

This corresponds to the standard rhyme definition in linguistics.

Example:

time
mind
kind

This makes the algorithm interpretable, which is important for research.

5. Stable Word Anchors for Visualization

Your HTML visualization currently highlights:

words

Example:

Twinkle twinkle little STAR
How I wonder what you ARE

If you move to phoneme spans, highlighting becomes harder because rhymes may cover:

part of a word
multiple words
overlapping segments

Your current pipeline produces clean visuals.

6. Useful Baseline System

Your current algorithm serves as an excellent baseline model.

Later you can compare:

Baseline: exact rhyme clustering
Similarity model
Phoneme-stream model

Which is extremely useful for:

evaluation
experiments
research
7. Easier Integration With Lyrics Data

Most lyric datasets are structured as:

line
word
token

Your current system aligns naturally with that structure.

The phoneme-stream system operates at a different level of abstraction, which makes integration harder.

Recommended Architecture

Instead of replacing your pipeline, keep both.

Pipeline A
Word-based rhyme detection
(end rhymes, schemes)

Pipeline B
Phoneme-stream rhyme detection
(internal / multiword rhymes)

Architecture:

Audio
↓
MFA alignment
↓
phoneme data
↓
───────────────
Pipeline A
word-level rhymes
───────────────
Pipeline B
phoneme-span rhymes
───────────────
↓
visualization

This gives Verse-DNA two complementary rhyme detectors.

Practical Recommendation

Do not discard your current pipeline.

It should remain responsible for:

end rhyme detection
rhyme scheme extraction
baseline evaluation

The phoneme-stream pipeline should handle:

internal rhymes
multiword rhymes
rap rhyme chains
One Important Observation

Your current pipeline is already very well structured for the baseline system. The phoneme-stream approach should be implemented as a new layer, not a replacement.
